## Архитектура и полномочия

`Users` хранится в `auth.users`; роль официанта представлена `restaurant_staff.role='waiter'`, без дублирования учётных записей. `restaurant_staff` связывает пользователя с конкретным рестораном; один аккаунт может работать в нескольких заведениях. Единственное актуальное назначение задаёт `dining_tables.waiter_id`, а `table_assignments` сохраняет интервалы и смены. При старте новой смены прошлые интервалы завершаются, новые добавляются.

Анонимным клиентам закрыты прямые чтения и записи всех бизнес-таблиц. Публичное меню доступно только через активный QR. Гостевые RPC проверяют непредсказуемый токен из двух UUIDv4, подтверждённое присутствие, срок действия, отзыв, ресторан и состояние сессии. Сервер хранит SHA-256 токена; браузер — исходный токен в sessionStorage, без помещения в URL. В этой архитектуре клиент обращается прямо к Supabase; HttpOnly cookie потребовала бы отдельного BFF. CSP ограничивает выполнение скриптов и доступ к backend.

Подтверждение присутствия не автоматическое: сотрудник должен видеть гостя за столом. Отдельное устройство требует отдельного подтверждения. До него меню/корзина доступны, а доступ к заказам и счёту запрещён. Токен действует до восьми часов либо до закрытия сессии. Продления истёкшего токена нет: нужна новая проверка присутствия. Запрос подтверждения действует пять минут.

Staff-команды проверяют роль и ресторан. Официант может работать со своими актуальными заказами/столиками; принятые лично заказы и собственные события доступны в истории после передачи столика. Администратор видит весь ресторан. Super Admin явно назначается владельцем инфраструктуры, обычная регистрация этой роли не даёт.

Идемпотентность хранит актор, UUID команды, SHA-256 действия/данных и результат. Повтор возвращает исходный результат, другой payload с тем же ключом отклоняется. Клиент сохраняет ожидающий ключ в sessionStorage до подтверждённого успеха, включая перезагрузку вкладки. Сервер ограничивает частоту гостевых записей и запросов присутствия. Auth дополнительно имеет собственные ограничения Supabase; периметровые ограничения IP рекомендуются при публичном размещении.

## Транзакции и ожидание

Порядок блокировок: столик → сессия → заказ → задания. Он применяется созданием заказа, закрытием, переназначением, принятием и обработчиком ожидания. Уникальный частичный индекс не допускает две открытые сессии одного столика. Все связанные записи заказа, снимки позиций, события и задания создаются в одной транзакции.

Сроки повторного уведомления/эскалации по умолчанию 120/180 секунд, фиксируются на заказе. Переназначение не сбрасывает их и время создания. Цвет: `<60` секунд зелёный, `60..120` жёлтый, `>120` красный. Браузер синхронизирует счётчик с серверным временем; сроки и реакцию определяет исключительно PostgreSQL.

Принятие единожды фиксирует `accepted_at`, `accepted_by`, `reaction_seconds`. Повторный приём не перезаписывает фактического принявшего. Отмена требует причины. Переходы строго последовательны: new → accepted → preparing → ready → served → completed; отмена допустима до completed. История статусов и событий не редактируется.

Обработчик выбирает просроченные задания с блокировками и пропуском занятых строк. Принятые/отменённые заказы не уведомляются. Уникальные ключи уведомлений исключают повторную запись. При принятии, отмене или передаче уже просроченного заказа факт просрочки сохраняется и без предварительного прохода Cron, с ответственным на этот момент. Cron проверяет каждые десять секунд, а не в браузере.

## Столики и завершение

Подтверждённая открытая сессия означает «Обслуживается», новый непринятый заказ — «Ожидает подтверждения». Запрос счёта сохраняется независимо от ожидания заказа: pending имеет приоритет, после принятия показывается bill. Новый дополнительный заказ снимает прежний запрос счёта и требует нового расчёта. Обычное закрытие допускается после завершения/отмены всех заказов. Администратор может принудительно отменить незавершённые заказы с причиной.

Закрытие отзывает все токены, отклоняет ещё не подтверждённые запросы присутствия и переводит стол в cleanup. Только подтверждение подготовки делает его free. Административный переход в free также закрывает сессию, а не оставляет действующие токены. Новые гости получают новую сессию без доступа к предыдущей. Сканирование cleanup-столика не освобождает его.

## Определения аналитики

Период `[начало, конец)` вычисляется в часовом поясе ресторана. Сегодня/вчера — календарные дни; неделя — последние семь календарных дней включая сегодня; месяц — с первого числа текущего месяца по сегодня. Произвольный период включает обе выбранные даты, максимум 367 календарных дней. Отсутствующая выборка среднего — `null`, отображается «—».

| Показатель | Правило |
|---|---|
| Обслуженные столики | Закрытые в периоде сессии по фактическому `closed_by`, повторные визиты считаются отдельно |
| Полученные заказы | Уникальные заказы с событием назначения сотруднику в периоде; при передаче заказ может учитываться у нескольких получателей |
| Принятые | Принятые в периоде по фактическому `accepted_by` |
| Средняя реакция / максимум ожидания | `reaction_seconds` принятых в периоде; время до передачи включается |
| Текущее максимальное ожидание | Отдельно, по новым заказам и текущему ответственному |
| Просрочки | Заказы с `overdue_at` в периоде по ответственному на срок просрочки |
| Сумма заказов | Снимок стоимости созданных в периоде заказов по первоначальному получателю; сумма отменённых выделена отдельно |
| Отменённые | События отмены в периоде по ответственному на момент отмены |
| Вызовы | События создания call в периоде по исходному получателю |
| Среднее обслуживание | `closed_at - opened_at` сессий, закрытых в периоде, по завершившему; подготовка после ухода исключена |
| Активные столики | Текущий снимок открытых сессий по актуальному ответственному; не привязан к историческому фильтру |
| График по часам | Создания заказов; разные UTC-часы при осеннем переводе времени сохраняются отдельными интервалами |
| Реакция ресторана | Среднее по всем соответствующим заказам, не среднее средних сотрудников |
| Пиковое время | Все часовые интервалы с максимальным числом созданий в периоде |

Администратор, принявший или закрывший заказ/сессию, отображается собственной строкой с ролью. Сумма заказов не является выручкой. Валюта после первого заказа фиксирована, что предотвращает смешивание сумм. Оценка реакции сопровождается активными столиками и количеством заказов, автоматического рейтинга только по скорости нет.
