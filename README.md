# QR Waiter

PWA для ресторана: React 19, TypeScript, Vite, Tailwind CSS 4, Supabase Auth/PostgreSQL/Realtime/Storage. Основной язык — украинский; доступны русский и английский. Полное ТЗ: [SPEC.md](SPEC.md). Карта реализации и правила аналитики: [IMPLEMENTATION.md](IMPLEMENTATION.md).

## Состояние проекта

Исходники приложения, миграции и серверные функции подготовлены. Бизнес-операции и RLS проверяются на настоящем PostgreSQL через PGlite. Подключение к вашему Supabase, отправка писем, облачный Cron/Realtime/Storage и доставка Web Push требуют настройки вашего проекта и не проверены на живом сервисе. Секретов в репозитории нет. Без переменных окружения приложение показывает экран настройки, без подставных заказов и статистики.

## Локальный запуск

Нужен Node.js 22.12+ или 24 LTS и npm. Команды выполняйте из папки проекта:

```powershell
Set-Location -LiteralPath 'K:\Разработка\Для ресторанов'
npm.cmd ci
Copy-Item -LiteralPath '.env.example' -Destination '.env'
# Заполните .env настоящими публичными параметрами своего Supabase.
npm.cmd run dev
```

Открыть `http://127.0.0.1:5173/`. Для проверки: `npm.cmd test`. Для сборки: `npm.cmd run build`. Для просмотра сборки: `npm.cmd run preview`.

В `.env`:

- `VITE_SUPABASE_URL` — URL проекта Supabase.
- `VITE_SUPABASE_ANON_KEY` — публичный anon/publishable ключ. Он допустим в браузере, доступ защищён RLS и RPC.
- `VITE_APP_URL` — окончательный адрес frontend без завершающего `/`. Установите его до печати QR; напечатанный код содержит этот адрес.
- `VITE_VAPID_PUBLIC_KEY` — публичный VAPID-ключ, если подключаете Web Push.

Service role, приватный VAPID-ключ и секрет очереди никогда не помещайте в `VITE_*`.

## Supabase

1. Создайте проект Supabase и установите URL/публичный ключ в `.env`.
2. В SQL Editor выполните по порядку файлы `supabase/migrations/202610140001_core.sql`, `202610140002_analytics.sql`, `202610140003_platform.sql`. Это начальные миграции новой БД; повторно не запускайте уже применённые файлы. Альтернатива — Supabase CLI `link` и `db push` с учётом вашей среды.
3. В Authentication → URL Configuration укажите Site URL и Redirect URLs для localhost и конечного домена. Разрешите регистрацию с подтверждением email. Настройте собственный SMTP для реальных приглашений персонала; стандартный почтовый сервис Supabase имеет ограничения на получателей.
4. Разверните Edge Function `invite-staff`. Она проверяет JWT через `auth.getUser`, активное членство и роль администратора до обращения к Auth Admin. Уже подтверждённый существующий аккаунт можно присоединить к другому ресторану; новый получает приглашение по email.
5. Задайте Edge secret `APP_ORIGIN` — точный frontend origin. Supabase автоматически предоставляет `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `SUPABASE_SERVICE_ROLE_KEY`; в локальной среде настройте их отдельно. `verify_jwt=false` в config.toml не отключает проверки пользователя внутри функций.

```powershell
npx supabase login
npx supabase link --project-ref YOUR_PROJECT_REF
npx supabase db push
npx supabase functions deploy invite-staff
npx supabase secrets set APP_ORIGIN=https://YOUR_FRONTEND_DOMAIN
```

Используйте либо SQL Editor, либо миграции CLI, не применяйте те же начальные файлы вторым способом к уже заполненной БД. Подставляйте свои значения вместо заглушек. Не сохраняйте CLI access token или database password в файлах проекта.

Миграция платформы включает серверный Cron каждые 10 секунд, публикацию Realtime для пяти таблиц и публичный bucket `menu-photos` с записью только администраторам соответствующего ресторана. Для изображений допустимы JPEG/PNG/WebP, до 5 MB. Проверить планировщик:

```sql
select jobname, schedule, active from cron.job where jobname = 'qr-waiter-waiting';
select status, return_message, start_time from cron.job_run_details order by start_time desc limit 20;
```

Задание сработает при первом проходе после срока; типичная задержка до 10 секунд. Пропущенные сроки после простоя обрабатываются при следующем запуске. Открытая страница не требуется. Контроль ожидания создаёт постоянные записи в Notifications независимо от настройки Push.

## Первый ресторан

1. Зарегистрируйте владельца на главной странице и подтвердите email.
2. Войдите, создайте ресторан, указав название и имя администратора.
3. В разделе «Команда» пригласите официантов. По письму приглашения сотрудник входит и задаёт пароль через «Налаштування → Змінити пароль».
4. Создайте категории и блюда, при необходимости добавьте опции и фотографии.
5. Создайте столики с ответственными сотрудниками, начните смену.
6. В разделе «Столики та QR» откройте меню столика или скачайте PNG/PDF. Персональный QR официанта требует выбора конкретного закреплённого столика.
7. Гость видит меню без регистрации и отправляет запрос присутствия. Официант проверяет, что человек действительно за указанным столом, и подтверждает запрос. Лишь после этого разрешаются заказы и просмотр счёта сессии.
8. Примите заказ и последовательно меняйте статусы до «Завершено». После завершения всех заказов закройте сессию; столик станет «Очікує звільнення». Подтвердите уход гостей и подготовку — столик станет свободным.

Администратор может отменять, переназначать и принудительно завершать сессию с причиной. Ресторан можно создать дополнительно в настройках. Онлайн-оплата не подключена: запрос счёта показывает сумму заказов, без утверждения об оплате.

## Super Admin

Регистрация в интерфейсе не выдаёт глобальные права. Владелец инфраструктуры назначает Super Admin вручную в SQL Editor, используя реальный UUID из Authentication → Users:

```sql
insert into public.super_admins(user_id) values ('YOUR_AUTH_USER_UUID');
```

После повторного входа раздел «Заклади» позволяет менять статус/название тарифа и передавать владение действующему администратору ресторана. «Тариф» пока является метаданными; оплата подписок отнесена ТЗ к будущему развитию.

## Web Push

Realtime, сохранённый inbox и резервное обновление работают без Push. Звук включается кнопкой сотрудника, после пользовательского жеста.

1. Выполните `npm.cmd run vapid` самостоятельно для генерации вашей пары VAPID-ключей. Сохраните приватный ключ вне репозитория.
2. Настройте Edge secrets `VAPID_PUBLIC_KEY`, `VAPID_PRIVATE_KEY`, `VAPID_SUBJECT` (например, `mailto:YOUR_ADMIN_EMAIL`) и собственный случайный `PUSH_DISPATCH_SECRET`.
3. Публичный ключ задайте в `VITE_VAPID_PUBLIC_KEY`, пересоберите frontend.
4. Разверните `push-dispatch`. Создайте в Supabase Vault секреты `qr_waiter_project_url` и `qr_waiter_push_secret`, затем выполните `supabase/schedule-push.sql`.
5. Сотрудник нажимает «Увімкнути push» и разрешает уведомления. Требуются HTTPS (localhost допускается) и поддерживаемый браузер; на iOS обычно требуется установленный PWA.

Очередь доставки имеет блокировку, повторные попытки, уникальный ключ на уведомление/устройство и удаляет подписки, возвращающие 404/410. Уведомление в Service Worker имеет `tag` по UUID, чтобы повторные доставки заменяли карточку. Абсолютную однократность доставки внешнего Push-сервиса гарантировать нельзя; журнал уведомлений и серверные эскалации в БД уникальны. Прочитанные и ставшие неактуальными уведомления о новых заказах исключаются из очереди.

Для защиты серверной отправки разрешены адреса Google FCM, Mozilla Push, Apple Push и Windows WNS. Новый провайдер требует явного добавления в ограничение endpoint в БД.

## GitHub и Cloudflare Pages

Репозиторий проекта: [mnacik1988/Menu-](https://github.com/mnacik1988/Menu-). Первоначальная реализация подготовлена в ветке `codex/qr-waiter-mvp` для проверки перед слиянием в main. Существующий начальный коммит сохранён; `.env`, node_modules и сборка исключены из Git.

Для получения этой реализации до слияния:

```powershell
git clone --branch codex/qr-waiter-mvp https://github.com/mnacik1988/Menu-.git
Set-Location -LiteralPath 'Menu-'
npm.cmd ci
```

Облачные ресурсы пока не настроены. В Cloudflare Pages подключите репозиторий и выберите нужную ветку: build command `npm run build`, output directory `dist`, Node 22.12+.

Задайте публичные переменные `VITE_*` в настройках сборки Pages, укажите production URL в Supabase Auth и `APP_ORIGIN`. `public/_redirects` обеспечивает открытие страницы по QR, `_headers` добавляет CSP и запрет встраивания. CSP разрешает стандартные Supabase-домены; для собственного backend-домена измените `connect-src`. После смены домена старые напечатанные QR автоматически не меняются — сохраните прежний домен/редирект или перепечатайте их.

Перед использованием в ресторане выполните живую проверку из [TEST-REPORT.md](TEST-REPORT.md): настоящие Auth-приглашения, два браузера, Cron при закрытых страницах, загрузку фото и Push.
